# 第一部分：认知框架

### 1.1 "蒸馏"是什么？

蒸馏（Distillation）在这里有两种完全不同的含义，必须先分清：

| | 模型蒸馏（Model KD） | 知识库蒸馏（KB Distillation） |
|---|---|---|
| **目标** | 让小模型学大模型的能力 | 从内容中提取结构化知识存入库 |
| **输入** | Teacher 模型权重/输出 | PDF、图片、视频、音频等原始内容 |
| **输出** | 更小的 Student 模型 | 文档、Skill、JSONL、Wiki 页面 |
| **消费者** | 推理系统 | RAG 系统、Agent、人类 |
| **你需要的** | ❌ 不是这个 | ✅ 就是这个 |

**你的需求 = 知识库蒸馏**：从多模态输入（图片/PDF/视频等）中提取知识，以某种格式入库。

---

### 1.2 为什么要做蒸馏，而不是直接存原文？

直接把原始内容扔进向量库（Raw RAG）有三个根本缺陷：

1. **冗余噪音**：一份 50 页 PDF 有效知识点可能只有 20 个，但你存了 50 页的 token
2. **知识隐式**：原文里的知识是隐式编码在自然语言和格式中的，模型每次都要重新推理
3. **无法跨文档**：同一个概念散落在 10 份文档里，RAG 只能逐个返回，无法综合

蒸馏把隐式知识变显式、把冗余内容压缩、把跨文档关联显式建立。

**核心比喻**：原始文档 = 原矿石；蒸馏结果 = 精炼金属。精炼后才能被高效使用。

---

### 1.3 两条路径，必须都走

```
多模态原始内容
        │
        ▼
┌───────────────────────────────────────────┐
│              蒸馏结果（分层）               │
│                                           │
│  基础层：Wiki 文档（Markdown 页面体系）    │
│  ├── 完整性保障，供检索和人类阅读          │
│  ├── 四层金字塔（原子→概念→摘要→跨文档）  │
│  └── 使用 Karpathy LLM-Wiki 模式持续维护  │
│                                           │
│  上层：Agent Skill（SKILL.md）            │
│  ├── 高频执行知识的可执行封装              │
│  ├── Agent 直接加载调用，无需重新推理      │
│  └── 从 Wiki 文档二次蒸馏出来             │
└───────────────────────────────────────────┘
```

**不是二选一，是先后关系**：先建 Wiki 文档库（完整性），再从中蒸馏 Skill（效率）。

---

### 1.4 四层金字塔模型（核心蒸馏架构）

来源：Kudra.ai 2026，目前最成熟的生产级蒸馏架构。

```
Level 4: Cross-Document Recollections（跨文档元知识）
         ↑ 多文档涌现的模式、对比、矛盾标注
Level 3: Document Abstracts（文档摘要）
         ↑ 单文档的目的、范围、主题概览
Level 2: Concepts（概念层）
         ↑ 多个 Atomic Insight 聚合的主题群
Level 1: Atomic Insights（原子洞察）
         ↑ 最小粒度事实，SVO 格式（主谓宾）
```

**压缩比**：每页约 13 个 Atomic Insight 压缩为约 1 个 Concept（13:1），消除冗余保留语义。

**检索分流**：
- 精确查询 → 检索 Atomic Insights（Level 1）
- 探索性查询 → 检索 Concepts + Abstracts（Level 2-3）
- 元查询 → 检索 Cross-Document（Level 4）

### 1.5 Karpathy LLM-Wiki 模式（持续维护机制）

核心思想：LLM 不只在查询时检索原始文档，而是**持续编译维护一个 Wiki**。每次 ingest 新内容时主动更新 Wiki，让知识复利增长。

```
raw/           ← 只读原始资料（永不删除）
  ├── source1.pdf
  ├── video_transcript.md
  └── image_captions.md

wiki/          ← LLM 维护的编译结果（持续更新）
  ├── index.md          # 总目录，每次 ingest 更新
  ├── log.md            # 时序操作日志
  ├── entity_pages/     # 实体页（人物/组织/产品）
  ├── concept_pages/    # 概念页（技术概念/领域术语）
  └── summaries/        # 每个 source 的摘要页
```

**Ingest 流程**（每添加一个新源）：
1. LLM 读取原始资料
2. 写 summary 页进入 wiki/summaries/
3. 更新 index.md（添加条目）
4. 更新相关 entity/concept 页（跨文档合并已有知识）
5. 在 log.md 追加操作记录
